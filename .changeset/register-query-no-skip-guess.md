`register_query` no longer drops rows on a guess, and neither tool pages on a page it cannot place. Where 1С ignores `$top` and sends, at a `skip`, exactly as many rows as it counted, `register_query` took them for the whole table (`$skip` ignored too) and returned the rows from `skip` on — but a count short of the rows (a `select` 1С counts rolled up and returns un-rolled) looks the same, and then the rows asked for were dropped. `register_query` now places its pages as `query` does: a page past `top` is cut to `top` from its start, and a page at a `skip` holding exactly as many rows as 1С counted — or, past `top`, more — is ambiguous: `hasMore` is `false` (the byte budget included), the summary names both readings and how to narrow instead, and its truncation hint no longer suggests paging with `skip`. Both tools: a page past `top` at a `skip` with more rows than counted no longer offers paging on (before, where 1С ignored `$skip` as well, each next `skip` returned the same first rows with `hasMore: true`). `register_query`: an empty page now ends the paging (`hasMore: false`) even where the parallel `/$count` reported more rows — before, it reported `hasMore: true` and a client paging by `returned` asked for the same page again. The response shape is unchanged; to read past an ambiguous page, narrow the call (`condition`, `period`, `filter`, `select` — or `filter` on `query`) so the rows fit in one page.
