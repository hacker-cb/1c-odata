**Breaking:** MCP `register_query` pages on the 1С server: each call reads one page (`$skip` / `$top`) and, in a parallel request, the exact row count (the table's `/$count`), instead of fetching up to 100 001 rows and slicing the page out of them. `total` is now exact however large the result — the `totalCapped` field, its "capped at N rows" summary note and the `ONEC_MCP_MAX_REGISTER_ROWS` environment variable are removed. Migration: drop `ONEC_MCP_MAX_REGISTER_ROWS` from the server's environment (it is ignored now) and stop reading `totalCapped`; `total` and `pagination.hasMore` carry the same meaning as before, without the cap. The count and the page are two requests, so on data changing meanwhile they can briefly disagree; if the count request fails, the call fails. A page of a heavy table now costs about 9–11 s on 1С (measured on a БП 3.0 `AccountingRegister_Хозрасчетный/Turnovers()` of 235 000 rows) where every page used to cost about 24 s and 232 MB transferred; a small table answers in tens of milliseconds as before. Should a 1С publication ignore `$top`, the page is cut back to `top` rows (paged from `skip` when the whole table came back) and the summary says so. Where 1С counts a `select` as grouped but returns its rows ungrouped, the rows outrun `total`: from that page on `hasMore` follows full pages and the summary says the count is not the number of rows.

`register_query` also takes an optional `orderBy` (`[{ field, dir? }]`, the same shape as `query`'s): it sorts on the 1С server, so with `top` it returns a top-N — e.g. the ten largest debit turnovers. Sorting costs 1С time on a big table. Without `orderBy` the rows come in 1С's own order, which stayed the same from page to page in tests but is not promised by 1С — pass `orderBy` over fields that identify a row when pages must not overlap or skip rows.
