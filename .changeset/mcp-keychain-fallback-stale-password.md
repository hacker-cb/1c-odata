Stored passwords now resolve **env → `credentials.json` → OS keychain** (was env → keychain → file). A password written while the keychain refused it — a locked keychain, `add_connection` / `set_credentials` / CLI `add` / `set-credentials` — went to the `credentials.json` fallback, but an old keychain copy that could not be deleted outranked it once the keychain answered again; after a re-pointed connection the old password went to the new server. The same happened where another process sharing the data directory wrote the file (`--insecure-storage`, or no keychain backend) and never touched the keychain. The file holds a password only where the keychain refused the newest write — a write the keychain takes deletes the file copy, and fails where it cannot — so reading it first always reads the newest password; the keychain copy is deleted best-effort. A host without a working keychain (headless Linux / CI) still falls back to the file as before. One consequence: a `credentials.json` with permissions looser than `0600` (or malformed) is read, and refused, before the keychain, so it now stops keychain-stored passwords from resolving too — `chmod 600` it or delete it.
