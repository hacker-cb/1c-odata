Function-import and register virtual-table URLs accept only a 1С metadata name (letters, digits, `_`) as the entity set and function name, rejecting anything else with `InvalidArgumentError`, and encode it as one path segment: a name carrying `/`, `?`, `#`, `%`, `(` or `..` — e.g. a `register` argument passed to MCP `register_query` — can no longer reach another path of the host with the connection's credentials, push `$top` into a URL fragment or address a single entity. A name already percent-encoded by the caller is rejected too — pass the plain (Cyrillic) name. Collection, key, `$count`, `create` and ValueStorage URLs reject an entity set that is empty, `.`, `..` or not encodable (a lone surrogate); `create` now percent-encodes the set name like the other URLs. Entity keys get the same guard: a string key must be a GUID (a 1С `Ref_Key`) and a composite key's field names must be 1С names, otherwise `InvalidArgumentError` — reachable through MCP `get_entity` and every entity handle (get / patch / put / delete / ValueStorage). A string the URL encoder cannot take (a lone UTF-16 surrogate) in a query option, a function-import argument or a key value fails with `InvalidArgumentError` instead of a raw `URIError`. Cyrillic names are percent-encoded on the wire as before. MCP `register_query` also stops reporting `hasMore: true` past the row cap: paging ends at the last fetched row, and the cap is still reported by `totalCapped` and the summary note.
