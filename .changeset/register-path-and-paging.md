**Breaking:** names and keys that reach a URL path are now checked, and what does not pass is an `InvalidArgumentError` before any request. Rejected now: an entity-set or function name in a function-import or register virtual-table call (`client.functions.X.Y`, `client.register(…)`, document `post()` / `unpost()`, MCP `register_query`) that is not a plain 1С metadata name (letters, digits, `_`) — including a name the caller already percent-encoded; a ValueStorage property that is not such a name; a string entity key that is not a GUID; a composite key that is empty, an array, or has a field name that is not a 1С name. Migration: pass the plain (Cyrillic) name, never a percent-encoded one; pass a string key only as a `Ref_Key` GUID; pass a composite key as an object whose field names are 1С names (e.g. `{ Recorder: '…guid…', LineNumber: '1' }`).

Function-import and register virtual-table URLs encode the entity set and function name as one path segment each: a name carrying `/`, `?`, `#`, `%`, `(` or `..` — e.g. a `register` argument passed to MCP `register_query` — can no longer reach another path of the host with the connection's credentials, push `$top` into a URL fragment or address a single entity. Collection, key, `$count`, `create` and ValueStorage URLs reject an entity set that is empty, `.`, `..`, has such a `/`- or `\`-separated part outside its parentheses and quotes, or is not encodable (a lone surrogate); `create` now percent-encodes the set name like the other URLs. Entity keys get the same guard, reachable through MCP `get_entity` (which now checks the GUID shape in its schema) and every entity handle (get / patch / put / delete / ValueStorage). A string the URL encoder cannot take (a lone UTF-16 surrogate) in a query option, a function-import argument or a key value fails with `InvalidArgumentError` instead of a raw `URIError`. Cyrillic names are percent-encoded on the wire as before. MCP `register_query` also stops reporting `hasMore: true` past the row cap: paging ends at the last fetched row, and the cap is still reported by `totalCapped` and the summary note.
